\title{A Comprehensive Security Framework for Autonomous AI Agents: Integrating Structural Guardrails, Behavioral Zero-Trust, and Post-Quantum Resilience}

\begin{abstract}
As Large Language Model (LLM) agents transition from passive chatbots to autonomous entities capable of executing system-level tools via protocols like the Model Context Protocol (MCP), they introduce a critical "Agency Gap." Traditional security perimeters are insufficient for protecting against prompt injection, semantic drift, and future cryptographic threats. This paper proposes a unified, three-tier security framework designed to protect agent-based systems across three dimensions: Space, Behavior, and Time. First, we establish \textit{Structural Guardrails} (Space) using AST-based static analysis and environment isolation to contain malicious code execution.
 Second, we implement \textit{Behavioral Zero-Trust} (Behavior) monitoring using a Mamba-based Sentinel to detect anomalous reasoning in real-time and enforce workload identity. Third, we ensure \textit{Temporal Sovereignty} (Time) by integrating Post-Quantum Cryptography (PQC) and remote attestation to guarantee long-term integrity and resilience against future quantum adversaries. Our evaluation demonstrates that this "Triple-Lock" architecture provides robust, multi-layered defense with minimal computational overhead, maintaining agent responsiveness while ensuring system-wide security.
\end{abstract}

\section{Introduction}
The transition of Large Language Models (LLMs) to autonomous agents represents a fundamental shift in computing. By leveraging the Model Context Protocol (MCP) \cite{mcp2024}, these agents can interact directly with host operating systems, manage sensitive data, and orchestrate complex API workflows. However, this "Agency" capability creates an unprecedented security surface. Traditional security perimeters are often ineffective against "Prompt Injection" attacks, where an attacker manipulates the LLM's goal-oriented reasoning to execute unauthorized system commands \cite{perez2022ignore}.

The OWASP Top 10 for LLM Applications \cite{owasp2023} identifies "Insecure Output Handling" (LLM02) and "Excessive Agency" (LLM08) as critical risks. Currently, many autonomous frameworks rely on "Alignment"---the probabilistic expectation that the LLM will follow safety guidelines. We argue that for mission-critical systems, behavioral alignment is a necessary but insufficient condition. We require a holistic, deterministic security architecture that ensures system integrity even if the model's logic is compromised.

This paper presents a comprehensive "Triple-Lock" framework for Agentic Security, addressing the lifecycle of an agent's action through three integrated dimensions (Fig. \ref{fig:overview_arch}):
\begin{enumerate}
    \item \textbf{Structural Containment (Space):} Establishing deterministic safety boundaries using AST inspection and environment isolation via remote MCP servers to ensure "Secure-by-Default" tool execution.
    \item \textbf{Behavioral Integrity (Behavior):} Implementing a Zero Trust Architecture (ZTA) where every action is verified by a verifiable workload identity and monitored by a Mamba-based "Reasoning Sentinel" to detect semantic anomalies.
    \item \textbf{Temporal Sovereignty (Time):} Protecting against future cryptographic threats (Shor's algorithm) using Post-Quantum Cryptography (PQC) to ensure the long-term confidentiality and non-repudiability of agent history.
\end{enumerate}

\section{Related Work}
Existing efforts to secure agents generally fall into three categories: \textit{Behavioral Filtering}, \textit{Structural Isolation}, and \textit{Governance Frameworks}. Behavioral filters like \textbf{Guardrails AI} and \textbf{LLM-Guard} \cite{llmguard2023} use secondary LLMs or pattern matching to scrub outputs, but often introduce significant latency and can be bypassed by complex semantic attacks. Isolation patterns, such as those evaluated in \textbf{AgentDojo} \cite{agentdojo2024}, focus on containing the impact of a compromise through sandboxing but do not inherently address the long-term integrity of the reasoning process.

Our framework aligns with the \textbf{NIST AI Risk Management Framework (AI RMF 1.0)} \cite{nistairmf2023} and \textbf{Zero Trust principles} (SP 800-207) \cite{nist2020zt}, treating every tool call as an untrusted workload. Furthermore, we address the "Store Now, Decrypt Later" (SNDL) threat by adopting NIST-standardized Post-Quantum Cryptography (PQC) primitives \cite{nistfips203, nistfips204}, providing a temporal dimension of security often overlooked in current agentic research such as \textbf{PromptArmor} \cite{promptarmor2024}.

\section{Threat Model}
We define four primary threat vectors for autonomous LLM agents:
\begin{enumerate}
    \item \textbf{Prompt Injection (Direct/Indirect):} Manipulating the agent's context to execute unauthorized commands or exfiltrate secrets \cite{greshake2023not}.
    \item \textbf{Semantic Drift/Malicious Intent:} An agent performing syntactically valid but semantically harmful actions (e.g., deleting a database file represented as a "document").
    \item \textbf{Secret Exfiltration:} Inadvertent transmission of API keys or PII during tool calls.
    \item \textbf{Quantum Retroactive Decryption:} Capturing current reasoning traces to decrypt them later using a quantum computer.
\end{enumerate}

\section{Tier 1: Structural Guardrails (Space)}
To ensure structural immunity, we adopt a "No-Shell" execution model where system operations are restricted to specialized tools (e.g., \texttt{execute\_python}).

\subsection{AST Inspection and Static Analysis}
Before execution, generated code is parsed into an Abstract Syntax Tree (AST). A whitelist-based scanner blocks dangerous modules (e.g., \texttt{os, socket, pty}) and built-in functions (e.g., \texttt{eval, exec}). Specifically, it ensures that \texttt{subprocess} calls never use \texttt{shell=True}, and detects reflection-based attacks (e.g., \texttt{\_\_subclasses\_\_}, \texttt{globals()}) to enforce a strict separation between executable and arguments.

\subsection{Path Guardrails and Resource Limits}
All file-related operations are restricted to a designated workspace via path resolution and symbolic link verification. To prevent resource exhaustion attacks, OS-level resource limits (\texttt{rlimit}) cap memory usage and execution time. Furthermore, the environment is sanitized by filtering sensitive environment variables (e.g., API keys) before passing them to the sub-process.

\subsection{Environment Isolation via MCP and Containers}
While static analysis provides structural guardrails, the framework achieves process isolation by leveraging the Model Context Protocol (MCP) to delegate high-risk tool execution to external, isolated environments. By connecting to MCP servers running within dedicated virtual machines (VMs) or Docker containers, the agent operates in a "Shared-Nothing" architecture. This approach ensures that even if a generated script bypasses static analysis, any malicious activity is contained within a disposable, restricted environment with no access to the host's primary filesystem or sensitive credentials. This multi-layered approach combines local structural safety with remote environment isolation, providing a robust defense-in-depth strategy.

\section{Tier 2: Behavioral Zero-Trust (Behavior)}
Identity ensures \textit{who} is calling the tool, while monitoring ensures \textit{why}.

\subsection{Workload Identity and ABAC}
Each agent instance is assigned a unique key pair. Every MCP tool call is accompanied by a signed \textbf{Identity Token} using the \textbf{COSE (CBOR Object Signing and Encryption)} format \cite{rfc9052}, containing assigned \textbf{Attribute-Based Access Control (ABAC)} claims. Using COSE's multi-signer structure, we integrate both classical (RSA) and PQC (ML-DSA) signatures into a single binary object. This avoids the 33\% size overhead associated with Base64-encoded JSON Web Tokens (JWT) and ensures that tool requests are non-repudiable and untampered. Remote servers verify this token to ensure the request originated from a legitimate agent and enforce strict tool access policies based on the execution context and resource attributes. Crucially, public keys and remote attestation manifests are distributed via an Out-of-Band (OOB) trusted channel (e.g., MDM or Secure Enclave). This architectural choice completely avoids the Trust-On-First-Use (TOFU) vulnerability\footnote{While the core protocol is designed for OOB provisioning to eliminate TOFU, the provided standalone reference implementation includes an optional bootstrap mode for environments lacking enterprise distribution infrastructure. This ensures immediate usability while allowing security-hardened deployments to disable TOFU via environment-specific configuration.} and eliminates the need for external verification servers, maintaining the CLI tool's self-contained nature and resilience against initial compromise.

\subsection{The Mamba Sentinel: Overcoming Dual-LLM Latency}
Current agentic security frameworks often rely on a "Dual-LLM" approach (using a secondary model to verify the intent of the primary model). However, our empirical testing demonstrates that this inherently introduces a massive $O(N^2)$ Transformer overhead, causing severe User Experience (UX) degradation (frequently adding multi-second latency per tool call). To resolve this, we move beyond the Dual-LLM intent analyzer to a \textbf{Mamba (State Space Model)} \cite{mamba2023} implementation as the primary, real-time monitoring engine. Running locally with pure NumPy, Mamba monitors the agent's reasoning tokens in real-time with $O(N)$ linear scaling. By calculating a ``Surprise Score'' (cross-entropy loss), the Sentinel detects statistical anomalies correlating with ``Jailbreaks'' or adversarial intent. 

\textit{Note on Evaluation:} In this proof-of-concept, the Sentinel is calibrated on a small dataset of benign reasoning traces. While this demonstrates the feasibility of using SSMs for sub-100ms intent monitoring, production deployments should scale with diverse training corpora to maintain robust detection rates.

\subsection{Reasoning Anomaly Detection: Predictive Pattern Analysis}
Complementing the behavioral analysis of the Sentinel, we implement a \textbf{Reasoning Anomaly Detector} as a unified integrity filter. While the Sentinel monitors the \textit{semantic} flow for intent drift, the Detector operates on the \textit{byte-level} patterns of the reasoning stream. It identifies sequences that exhibit high statistical unpredictability (Surprise) relative to the learned baseline. By utilizing the Mamba model's internal surprise score (cross-entropy), the system can detect both technical credentials and structurally anomalous logic that deviates from intended agent behavior. This approach provides a context-aware guardrail that moves beyond static entropy-based methods towards an adaptive, model-driven security posture.

\subsection{Bi-directional Verification with ResponseSigner}
To ensure the integrity of the entire tool execution loop, we implement \textbf{Bi-directional Verification}. While the agent signs the tool request via an Identity Token, high-risk write tools (\texttt{edit\_file}, \texttt{create\_or\_overwrite\_file}) embed a \textbf{ResponseSigner} PQC signature (ML-DSA) in their return value, binding the response content to a unique \texttt{verification\_id}. The \texttt{tool\_executor} layer verifies this signature before passing the result to the LLM, preventing ``Man-in-the-Middle'' manipulation of tool outputs and ensuring that the model's subsequent reasoning is grounded in untampered observations.

Furthermore, when the Mamba Sentinel raises a \textbf{RED} alert on a high-risk tool, CASS activates ``strict enforcement.'' Rather than autonomously blocking execution---which risks UX degradation and opaque failures---the system mandates a \textbf{Human-in-the-Loop (HITL)} approval dialog, surfacing the anomaly score and requiring explicit human confirmation. This design is consistent with the NIST AI Risk Management Framework (AI RMF) principle of maintaining human oversight over consequential AI actions.

\subsection{Quantum-Safe Identity and Hybrid Encryption}
We upgrade the workload identity using \textbf{ML-DSA-65} (FIPS 204). Audit logs, which contain sensitive reasoning traces, are protected using \textbf{ML-KEM-768} (FIPS 203) hybrid encryption. Our implementation supports \textbf{PQC Agility}, dynamically switching between ML-DSA-44, 65, and 87 variants based on the risk level determined by CASS. As described in Section~\ref{sec:arch}, three physically separate key pairs are provisioned on disk to satisfy cryptographic isolation across security tiers.

\subsection{PQC Remote Attestation and Audit Continuity}
The client generates a SHA-256 manifest of its core security code (covering six critical files including \texttt{identity.py}, \texttt{policy.py}, and \texttt{audit.py}), signed with an ML-DSA private key. This allows the server to verify that the agent is running on an ``Authentic Stack'' where Tier 1 guardrails are active. In strict mode (\texttt{LLM\_CLI\_STRICT\_SECURITY=1}), the absence of a pre-provisioned manifest causes startup to abort, eliminating Trust-On-First-Use (TOFU) risk in production deployments.

To ensure the tamper-evidence of long-running logs, we implement \textbf{Audit Chain Continuity} using a combination of two mechanisms: (1) on log rotation, overflowing entries are written to a timestamped archive file and a signed \emph{snapshot anchor} entry is prepended to the remaining log, recording both the \texttt{snapshot\_prev\_hash} and \texttt{snapshot\_first\_hash} to maintain chain verifiability across file boundaries; (2) a binary \textbf{Merkle Tree} is computed over all log entries, producing a single Merkle Root that can be externally anchored (e.g., to a blockchain or managed immutable log service) to provide compact, publicly verifiable proof of log integrity.

\section{System Architecture and Integration}
\label{sec:arch}

To synthesize the three tiers into a cohesive ``Triple-Lock'' architecture, we introduce \textbf{Context-Adaptive Security Scaling (CASS)}. CASS serves as the central orchestration engine, dynamically integrating the spatial, behavioral, and temporal defenses based on the specific risk profile of each tool execution request (Fig. \ref{fig:detailed_arch}).

\subsection{CASS Orchestration Logic}
CASS determines the required security posture by mapping the requested tool and its arguments to one of three risk levels defined in the system's \texttt{defaults.toml}. As shown in Table \ref{tab:cass_matrix}, this mapping ensures that computational resources are allocated proportionally to the security risk. High-risk tools such as \texttt{execute\_python} trigger the maximum security posture, including AST-based strict filtering, ML-DSA-87 signatures, and ML-KEM-768 audit encryption.

\subsection{Hybrid Identity Tokens (COSE/RFC 9052)}
To ensure verifiable workload identity without the overhead of JSON-based JWT, we implement a native \textbf{COSE\_Sign} structure (CBOR tag 98) as defined in RFC 9052. Unlike conventional implementations, our framework utilizes a dual-signature approach that combines a classical RS256 (RSA-PKCS1v15) signature for backward compatibility with an ML-DSA signature (using the IANA-pending \texttt{alg=-48} identifier) for post-quantum integrity. 

By implementing this directly via \texttt{cbor2} and \texttt{cryptography} instead of high-level libraries like \texttt{pycose}, we achieve a zero-dependency, fully auditable signature process. This ensures that the identity claim is non-repudiable and immune to ``Store Now, Decrypt Later'' (SNDL) attacks against the authentication channel.

\subsection{Cryptographic Isolation and Attestation}
To prevent cross-tier compromise, the architecture enforces physical separation of cryptographic material. Three independent ML-DSA key pairs (\texttt{id\_pqc\_l2.key}, \texttt{id\_pqc\_l3.key}, \texttt{id\_pqc\_l5.key}) are provisioned, ensuring that a compromise of a Level 2 key (used for low-risk tools) does not grant the ability to sign for High-Risk (Level 5) operations.

Furthermore, the framework ensures the integrity of the execution environment through a signed \textbf{Integrity Manifest}. Upon startup, the \texttt{IntegrityVerifier} generates a SHA-256 hash of six critical security modules: \texttt{identity.py}, \texttt{policy.py}, \texttt{audit.py}, \texttt{pqc.py}, \texttt{static\_analyzer.py}, and \texttt{cass.py}. Remote MCP servers verify this attestation before accepting any tool requests, ensuring that the agent is running on an unmodified, authentic security stack. In \texttt{STRICT} mode, any modification to these files results in a refusal to boot, effectively eliminating the risk of runtime injection into the security logic.

The results indicate that while newer architectures like Zen 4 (Ryzen 5 8540U) significantly accelerate pure-Python PQC operations, older systems (i7-7700) still provide sufficient performance for real-time agentic workflows. The $O(N)$ scaling of the Mamba Sentinel ensures that even on the legacy i7-7700, reasoning monitoring adds only $\approx$57ms per 100 tokens. Future optimizations will involve migrating to Rust-backed native PQC primitives (e.g., via the \texttt{cryptography} library) once NIST standards reach stability in mainline Python security packages, further reducing overhead without compromising the system's cross-platform portability.

\section{Conclusion}
Securing autonomous agents requires a transition from probabilistic "alignment" to a multi-dimensional, deterministic framework. By integrating Structural Guardrails, Behavioral Zero-Trust, and Post-Quantum Resilience, our framework provides a "Triple-Lock" defense that scales across the spatial, behavioral, and temporal domains of agentic execution. This holistic approach is essential for maintaining human control and data sovereignty as AI agents evolve into active participants in our digital infrastructure.
