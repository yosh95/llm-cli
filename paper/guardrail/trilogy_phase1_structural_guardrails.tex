\begin{abstract}
The rapid proliferation of Large Language Model (LLM) agents, empowered by the Model Context Protocol (MCP), has enabled autonomous interaction with host operating systems and external APIs. However, this "Agency" introduces a critical security gap: the susceptibility of LLMs to prompt injection and malicious tool misuse. This paper presents \textbf{Phase 1: Guardrails (Pre-execution Security)}, the foundational component of a technical trilogy focused on agentic security. We propose a "Secure-by-Default" containment architecture that treats LLM-generated code as an untrusted payload. Key contributions include: (1) a "No-Shell" execution model that eliminates shell-injection vulnerabilities, (2) a multi-stage validation pipeline incorporating AST-based static analysis and entropy-driven secret detection, and (3) a lightweight Linux-based isolation layer using unprivileged containers. Our experimental evaluation demonstrates that these structural guardrails effectively mitigate system-level compromises with negligible performance overhead ($<$20ms latency), establishing a robust baseline for autonomous agent safety.
\end{abstract}

\section{Introduction}
The evolution of Large Language Models (LLMs) from text-generators to autonomous agents has introduced a new class of security vulnerabilities. Modern agents utilize the Model Context Protocol (MCP) \cite{mcp2024} to interact with the physical and digital world, executing code, managing files, and accessing remote APIs. This "Agency" capability creates a significant gap between the AI's intent and the system's safety. Granting an AI agent raw shell access is equivalent to providing a persistent, non-deterministic remote shell to an entity susceptible to prompt injection.

We identify this challenge as the \textit{Structural Vulnerability of Autonomous Systems}. Traditional security assumes a human user with a stable identity and intent. AI agents, however, operate in a high-entropy reasoning space where a single adversarial prompt can "jailbreak" the agent's logic, causing it to generate harmful system commands.

This paper is the foundational installment of a technical trilogy dedicated to agent security:
\begin{itemize}
    \item \textbf{Phase 1: Guardrails (Pre-execution Security).} The current work, focusing on structural immunity and containment to prevent unauthorized actions at the point of inception.
    \item \textbf{Phase 2: Zero Trust (Execution Security) \cite{ando2026zerotrust}.} Focuses on spatial security and behavioral integrity monitoring via Mamba-based Sentinels.
    \item \textbf{Phase 3: Post-Quantum (Temporal Security) \cite{ando2026pqc}.} Focuses on long-term integrity and quantum-resistant governance.
\end{itemize}

In Phase 1, we advocate for a \textbf{Secure-by-Default Guardrail} architecture. Our contribution is a unified security framework that treats the LLM's output as an inherently untrusted payload, subjecting it to multi-layered static and dynamic isolation before execution.

\section{Design Principles}
To ensure robust security in autonomous agents, we adhere to four core principles:
\begin{enumerate}
    \item \textbf{Secure-by-Default:} Security is not an optional configuration but a structural requirement. No tool execution occurs without passing all guardrail layers.
    \item \textbf{Defense-in-Depth:} Multiple independent layers (AST analysis, OS sandboxing, entropy scanning) ensure that failure in one layer does not lead to a full system compromise.
    \item \textbf{Principle of Least Privilege:} The execution environment is restricted to the minimum set of files, modules, and network resources required for the task.
    \item \textbf{Human-in-the-Loop (HITL) Validation:} Critical system-altering actions require explicit human approval, mediated by a clear explanation of the agent's intent.
\end{enumerate}

\section{Related Work}
Existing autonomous frameworks like AutoGPT or BabyAGI often rely on permissive shell access, making them vulnerable to prompt injection attacks where the agent is tricked into executing malicious commands (e.g., \texttt{rm -rf /}). While tools like \textit{Guardrails AI} provide schema validation for JSON outputs, they lack low-level system containment. 

Recent research has identified "Principled Isolation Patterns" \cite{masood2024sandboxed} and benchmarked agent defenses using environments like \textit{AgentDojo} \cite{agentdojo2024}. However, many defenses focus on \textit{behavioral alignment}, which is probabilistic. Our approach shifts the focus to \textit{structural containment}, ensuring that even a compromised LLM cannot breach the host system's integrity.

\section{Threat Model}
We define three primary threat vectors for autonomous LLM agents:
\begin{enumerate}
    \item \textbf{Prompt Injection (Direct/Indirect):} An attacker manipulates the agent's context (e.g., via a malicious website) to execute unauthorized system commands \cite{perez2022ignore}.
    \item \textbf{Secret Exfiltration:} The agent accidentally leaks API keys or sensitive PII to a 3rd-party LLM provider during tool calls.
    \item \textbf{Resource Denial of Service (DoS):} Maliciously generated code causing CPU exhaustion or disk space depletion.
\end{enumerate}

\subsection{Layer 1: The "No-Shell" Execution Model}
Raw shell execution (\texttt{/bin/sh -c}) is structurally vulnerable because it conflates data and code. \texttt{llm-cli} adopts a "No-Shell" model where system operations are restricted to a specialized \texttt{execute_python} tool. By executing Python code via \texttt{subprocess.run(args, shell=False)}, we eliminate shell-injection vectors. The agent must express intent in a structured programming language (Python), which is amenable to static analysis.

\subsection{Layer 2: Static Analysis and AST Inspection}
The generated code is parsed into an Abstract Syntax Tree (AST) before execution. The system applies a whitelist-based security scanner:
\begin{itemize}
    \item \textbf{Module Blacklisting:} Prevents \texttt{import os, subprocess, socket}.
    \item \textbf{Function Blacklisting:} Blocks \texttt{eval(), exec(), open()} (when outside whitelisted paths).
    \item \textbf{Logic Inspection:} Detects \texttt{__subclasses__} or \texttt{getattr} abuse to bypass imports.
\end{itemize}

\subsection{Layer 3: Path Guardrails and Resource Limits}
All file-related operations are restricted to a designated workspace. We implement \textbf{Path Guardrails} that resolve symlinks and verify that all targets reside within the allowed directory. 
Furthermore, we apply \textbf{OS-level Resource Limits} (\texttt{rlimit}):
\begin{itemize}
    \item \textbf{Memory:} Capped at 1GB (RLIMIT\_AS).
    \item \textbf{CPU Time:} 300s timeout per execution.
\end{itemize}

\subsection{Layer 4: Entropy-Based Secret Detection}
To prevent credential leaks, we monitor the \textbf{Shannon Entropy} of the agent's output:
\begin{equation}
H(X) = -\sum_{i=1}^{n} P(x_i) \log_b P(x_i)
\end{equation}
High-entropy strings (e.g., API keys) are detected and redacted before they are sent to the LLM provider. This provides a zero-day defense against leaking secrets that do not match known regex patterns.

\subsection{Layer 5: Linux Sandboxing (Bubblewrap)}
The final containment is provided by \textbf{Bubblewrap} (\texttt{bwrap}), creating an unprivileged namespace with:
\begin{itemize}
    \item Private, empty \texttt{/tmp} and \texttt{/home} directories.
    \item Read-only mounts for system binaries (\texttt{/usr}, \texttt{/lib}).
    \item No network access (by default) and no host PID visibility.
\end{itemize}

\section{Conclusion}
Securing autonomous agents requires a departure from behavioral "alignment" toward structural, multi-layered guardrails. By combining a "No-Shell" model, AST inspection, and OS-level sandboxing, \texttt{llm-cli} provides a robust foundation for safe tool execution. This Phase 1 architecture ensures system integrity, setting the stage for Phase 2, which addresses behavioral anomalies via Zero-Trust monitoring.
