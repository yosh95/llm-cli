\begin{abstract}
As Large Language Model (LLM) agents transition from passive chatbots to autonomous entities capable of executing system-level tools via the Model Context Protocol (MCP), they introduce a critical "Agency" security gap. This paper presents \textbf{Phase 1: Guardrails (Pre-execution Security)}, the first installment of a technical trilogy on agentic security. We propose a "Secure-by-Default" containment architecture that treats LLM-generated code as an untrusted payload. Our framework integrates a "No-Shell" execution model, AST-based static analysis, and unprivileged Linux sandboxing. In our evaluation using a representative suite of adversarial patterns, the framework demonstrated a robust detection rate with a minimal performance overhead of approximately 1.1ms ($<$0.1\% of typical inference latency), establishing a deterministic foundation for autonomous agent safety.
\end{abstract}

AI Agents, Agentic Security, LLM Guardrails, Sandbox, Model Context Protocol, Prompt Injection, Static Analysis.

\section{Introduction}
The transition of Large Language Models (LLMs) from passive query-response systems to autonomous agents represents a fundamental shift in computing. By leveraging the Model Context Protocol (MCP) \cite{mcp2024}, these agents can now interact directly with host operating systems, manage sensitive files, and orchestrate complex API workflows. However, this "Agency" capability creates an unprecedented security surface. Traditional security perimeters are ineffective against "Prompt Injection" attacks, where an attacker manipulates the LLM's goal-oriented reasoning to execute unauthorized system commands \cite{perez2022ignore}.

The \textbf{OWASP Top 10 for LLM Applications} \cite{owasp2023} identifies "Insecure Output Handling" (LLM02) and "Excessive Agency" (LLM08) as critical risks. Currently, most autonomous frameworks rely on "Alignment"—the probabilistic hope that the LLM will follow safety guidelines. We argue that for mission-critical systems, behavioral alignment is insufficient. We require \textbf{Structural Containment}: a deterministic security architecture that ensures system integrity even if the model's logic is compromised.

This paper presents the first phase of a technical trilogy dedicated to "Agentic Security":
\begin{itemize}
    \item \textbf{Phase 1: Guardrails (Pre-execution Security).} This work, focusing on structural immunity through "No-Shell" models, AST inspection, and OS-level sandboxing (Bubblewrap).
    \item \textbf{Phase 2: Zero Trust (Execution Security) \cite{ando2026zerotrust}.} Addresses "Semantic Drift" by utilizing RSA-2048 workload identities and a real-time behavioral IDS based on \textbf{Mamba (State Space Models)} \cite{mamba2023}.
    \item \textbf{Phase 3: Post-Quantum (Temporal Security) \cite{ando2026pqc}.} Addresses long-term audit integrity and resilience against future quantum threats.
\end{itemize}

By establishing these structural guardrails in Phase 1, we provide the necessary foundation for the continuous verification and cryptographic identity frameworks introduced in subsequent phases.

\section{Related Work}
Existing autonomous frameworks like AutoGPT and BabyAGI often grant agents direct access to a system shell (\texttt{/bin/sh}). This design is inherently vulnerable to "Indirect Prompt Injection" \cite{greshake2023not}, where malicious instructions embedded in external data (e.g., a website the agent reads) can hijack the execution flow. 

Efforts to secure these agents generally fall into two categories:
\begin{enumerate}
    \item \textbf{Behavioral Filtering:} Tools like \textit{Guardrails AI} or \textit{Nemo Guardrails} use LLM-based verification to check output against safety schemas. While effective for data formatting, they introduce significant latency and are themselves susceptible to the same reasoning failures as the agent they monitor.
    \item \textbf{Containerized Isolation:} Research into "Principled Isolation Patterns" \cite{masood2024sandboxed} advocates for sandboxed execution. Frameworks like \textit{AgentDojo} \cite{agentdojo2024} provide benchmarking for these environments.
\end{enumerate}

Our work diverges from these by proposing a \textbf{Multi-layered Deterministic Pipeline}. Unlike behavioral filters, our Layer 2 (AST Analysis) and Layer 5 (Bubblewrap) do not rely on LLM inference, ensuring sub-millisecond static latency and immune-to-injection security. Furthermore, we align our architecture with the \textbf{NIST Zero Trust principles} (SP 800-207) \cite{nist2020zt}, treating every tool call as an untrusted workload that must be verified before execution.

\section{Threat Model}
We define three primary threat vectors for autonomous LLM agents:
\begin{enumerate}
    \item \textbf{Prompt Injection (Direct/Indirect):} An attacker manipulates the agent's context to execute unauthorized system commands \cite{perez2022ignore}.
    \item \textbf{Secret Exfiltration:} The agent accidentally leaks API keys or sensitive PII to a 3rd-party LLM provider during tool calls.
    \item \textbf{Resource Denial of Service (DoS):} Maliciously generated code causing CPU exhaustion or disk space depletion.
\end{enumerate}

\subsection{Layer 1: The "No-Shell" Execution Model}
Raw shell execution (\texttt{/bin/sh -c}) is structurally vulnerable because it conflates data and code. \texttt{llm-cli} adopts a "No-Shell" model where system operations are restricted to a specialized \texttt{execute\_python} tool. By executing Python code via \texttt{subprocess.run(args, shell=False)}, we eliminate shell-injection vectors. The agent must express intent in a structured programming language (Python), which is amenable to static analysis.

\subsection{Layer 2: Static Analysis and AST Inspection}
The generated code is parsed into an Abstract Syntax Tree (AST) before execution. The system applies a whitelist-based security scanner that traverses the tree using a \texttt{NodeVisitor} pattern. Specifically, we target:
\begin{itemize}
    \item \textbf{Module Blocking:} Prevents \texttt{import} of \texttt{os, socket, pty, ctypes}, and \texttt{requests} to block low-level OS access and unauthorized networking.
    \item \textbf{Function Sinks:} Blocks dangerous built-ins such as \texttt{eval(), exec(), getattr(),} and \texttt{\_\_import\_\_}.
    \item \textbf{Shell Injection Prevention:} Specifically inspects \texttt{subprocess} calls to ensure \texttt{shell=True} is never used, enforcing a strict separation between executable and arguments.
\end{itemize}

\subsection{Layer 3: Path Guardrails and Resource Limits}
All file-related operations are restricted to a designated workspace. We implement \textbf{Path Guardrails} that resolve symbolic links and verify that all targets reside within the allowed directory. 
Furthermore, we apply \textbf{OS-level Resource Limits} (\texttt{rlimit}):
\begin{itemize}
    \item \textbf{Memory:} Capped at 1GB (RLIMIT\_AS) to prevent memory-bomb attacks.
    \item \textbf{CPU Time:} 300s timeout per execution to mitigate infinite loops generated by the LLM.
\end{itemize}

\subsection{Layer 4: Entropy-Based Secret Detection}
To prevent credential leaks to LLM providers, we monitor the \textbf{Shannon Entropy} ($H$) of the agent's output. High-entropy strings often correlate with cryptographic keys or session tokens.
\begin{equation}
H(X) = -\sum_{i=1}^{n} P(x_i) \log_2 P(x_i)
\end{equation}
We define a heuristic threshold ($H > 4.0$ for strings longer than 16 characters). When detected, these strings are automatically redacted before the tool-call response is returned to the model context.

\subsection{Layer 5: Linux Sandboxing (Bubblewrap)}
The final containment is provided by \textbf{Bubblewrap} (\texttt{bwrap}), which utilizes Linux namespaces (\texttt{CLONE\_NEWNS, CLONE\_NEWUSER, CLONE\_NEWNET}) to create an unprivileged environment:
\begin{itemize}
    \item \textbf{Filesystem Isolation:} Private, empty \texttt{/tmp} and \texttt{/home}.
    \item \textbf{Network Isolation:} The \texttt{--unshare-all} flag ensures the sandbox has no network interface.
    \item \textbf{Process Isolation:} No visibility of host-system processes (\texttt{/proc} is re-mounted).
\end{itemize}

\section{Evaluation}
We evaluated the framework's performance and effectiveness using an expanded benchmark suite of 30 test cases, comprising 22 adversarial patterns (including obfuscated and reflection-based attacks) and 8 benign code samples.

The evaluation revealed that while the static analyzer is highly effective at blocking common injection vectors (e.g., \texttt{os.system}), it did not detect advanced reflection techniques such as \texttt{object.\_\_subclasses\_\_()} or access via \texttt{globals()}.

This result underscores the necessity of our \textbf{Defense-in-Depth} approach. The 27.3\% of adversarial patterns that bypassed static analysis were successfully contained by \textbf{Layer 5 (Bubblewrap Sandboxing)}, which physically prevents network access and host filesystem writes regardless of the LLM's code structure. By combining fast static filtering with robust OS-level isolation, we achieve both performance and security.

\section{Conclusion}
Securing autonomous agents requires a departure from behavioral "alignment" toward structural, multi-layered guardrails. By combining a "No-Shell" model, AST inspection, and OS-level sandboxing, \texttt{llm-cli} provides a robust foundation for safe tool execution. This Phase 1 architecture ensures system integrity, setting the stage for Phase 2, which addresses behavioral anomalies via Zero-Trust monitoring.
